# 한국어 기술 글쓰기

## 이 스킬이 존재하는 이유

개발 글이 어색해지는 지점은 두 곳입니다.

첫째는 **용어**입니다. "리턴값을 반환합니다", "디펜던시를 의존성 배열에 넣습니다"처럼 한 글 안에서 영어, 음차, 번역어가 뒤섞이거나, 반대로 "갈고리(Hook)를 부릅니다"처럼 아무도 안 쓰는 번역어를 억지로 만듭니다. 기준이 없으면 문장마다 감으로 고르게 되고, 결과는 글마다 달라집니다.

둘째는 **문장 구조**입니다. 영어 자료를 읽고 쓰거나 LLM이 쓰면 "당신의", "~에 의해 호출되어집니다", "~하는 것을 허용합니다" 같은 영어 구조가 그대로 남습니다. 뜻은 맞는데 읽고 싶지 않은 글이 됩니다.

이 스킬은 두 가지를 각각 한 곳에서 정합니다. 용어는 `references/terms/`, 문장은 `references/sentences.md`입니다. 번역에만 필요한 절차는 `references/translating.md`에 따로 있어서, 새로 쓸 때는 읽지 않아도 됩니다.

## 구조

```
korean-tech-writing/
├── SKILL.md                  ← 지금 읽는 문서. 절차
├── references/
│   ├── terms/
│   │   ├── common.md         ← 용어 판단 순서, 공통 용어집, 표기 규칙(백틱, 병기, 조사)
│   │   ├── react.md          ← React 전용 용어와 react.dev 보존 대상
│   │   └── adding.md         ← 용어·프레임워크 파일 추가 절차와 양식
│   ├── sentences.md          ← 문체, 문장 부호, 번역투, AI 말투
│   └── translating.md        ← 번역 전용: 원문 확보, 보존 대상, 점검
└── scripts/
    └── measure-terms.sh      ← 공식 번역 저장소에서 표기 빈도 실측
```

## 작업 절차

### 1. 글 종류와 문체를 정합니다

무엇을 쓰는지에 따라 문체가 정해집니다. 기본값은 이렇습니다.

| 글 종류 | 문체 |
|---|---|
| README, 기술 문서, 번역, 기술 블로그, 여러 줄 주석 | 습니다체 |
| PR 본문, 이슈 본문 | 습니다체 |
| 커밋 메시지, PR 제목, 이슈 제목 | 명사구 |
| UI 문구 | 해요체 |

사용자가 문체를 지정했거나, 저장소에 문체 규약(`docs/korean-style.md`, `CONTRIBUTING.md`, `commitlint` 설정, 기존 커밋 이력)이 있으면 그쪽이 우선합니다. 저장소 안에서 작업 중이면 쓰기 전에 한 번 확인하세요. 남의 저장소 관행을 무시하고 이 스킬의 기본값을 밀어붙이면 오히려 어색해집니다.

번역이면 이 단계에서 [references/translating.md](references/translating.md)를 읽습니다.

### 2. 용어를 정합니다

[references/terms/common.md](references/terms/common.md)를 읽습니다. 다루는 프레임워크의 파일(`terms/react.md` 등)이 있으면 함께 읽고, 두 곳이 어긋나면 프레임워크 파일이 우선합니다.

용어집에 없는 단어는 이 순서로 판단합니다.

1. 코드에 나오는 이름, 제품명, 약어는 영어로 둡니다 (`useState`, React, API)
2. 공식 한국어 문서에 정착된 표기를 따릅니다 (컴포넌트, 반환)
3. 공식 번역어가 현업에서 거의 안 쓰이면 현업 표기를 씁니다 (엣지 케이스)
4. 정착된 표기가 없으면 억지 음차 대신 한국어로 풀어 씁니다

표기는 이렇게 합니다.

- **백틱**은 코드에 실제로 나오는 이름에만 씁니다. `useState`는 백틱, React는 백틱 없이. 단, 커밋 메시지에는 백틱을 쓰지 않습니다(렌더링되지 않아 문자 그대로 보입니다).
- **영어 병기**는 번역어만 보고 원어를 떠올리기 어려울 때, 첫 등장에 한 번만 합니다. 멱등성(idempotency).
- **조사**는 철자가 아니라 읽는 소리의 받침으로 정합니다. API를, URL을, `useState`를.

정한 뒤에는 글 전체에서 같은 개념을 같은 말로 씁니다.

### 3. 문장을 씁니다

[references/sentences.md](references/sentences.md)를 따릅니다. 처음부터 규칙을 지키며 쓰는 게 나중에 고치는 것보다 훨씬 쌉니다. 특히 효과가 큰 것들입니다.

| 습관 | ✗ | ✓ |
|---|---|---|
| 인칭 대명사 | 당신의 컴포넌트는 | 컴포넌트는 |
| 무거운 술어 | ~하는 것을 허용합니다 | ~할 수 있습니다 |
| 이중피동 | 호출되어집니다 | 호출됩니다 |
| "의" 연쇄 | 컴포넌트의 state의 업데이트 | 컴포넌트 state 업데이트 |
| 긴 관형절 | (수식어가 주어 앞에 쌓인 한 문장) | 두세 문장으로 나누기 |
| 줄표 | 비워야 합니다 — 그렇지 않으면 | 비워야 합니다. 그렇지 않으면 |
| 꼬리 문장 | 이를 통해 더 나은 경험을 제공합니다 | (삭제) |

### 4. humanizer로 AI 말투를 점검합니다

LLM이 쓴 한국어에는 쉼표 과다, 균일한 문장 길이, 명사 과다 같은 흔적이 남습니다. 세어 보기 전에는 잘 안 보여서 눈으로 읽는 것으로는 대신할 수 없습니다. 그래서 다음 글은 사용자에게 내놓기 전에 **Skill 도구로 `humanizer`를 호출합니다.**

- 대상: README, 기술 문서, 번역, 기술 블로그, 여러 문단짜리 PR·이슈 본문
- 생략: 커밋 메시지, 제목, 짧은 UI 문구, 몇 줄짜리 주석 (도구를 돌리는 비용이 글보다 큽니다)

```
Skill(skill: "humanizer")
```

`humanizer`가 설치되어 있지 않거나 호출이 실패하면 건너뛰지 말고, [sentences.md](references/sentences.md) 4절 항목을 하나씩 직접 세어 가며 점검합니다. 특히 문장마다 쉼표 수와 문장 길이 변화를 실제로 셉니다. 결과를 내놓을 때 "`humanizer` 없이 직접 점검했다"고 한 줄 알립니다.

**넘기는 것**은 산문뿐입니다. 코드 블록, 헤딩 앵커, 링크 URL, 프론트매터, MDX 태그는 넘기지 않습니다.

**humanizer 규칙 중 적용하지 않는 것**이 있습니다. 두 스킬의 전제가 어긋나는 지점이라 그대로 받으면 1~2단계에서 맞춘 것이 깨집니다.

| humanizer 항목 | 처리 |
|---|---|
| 패턴 24 경어체 균일성 | **무시합니다.** humanizer는 균일한 `~습니다`를 AI 신호로 보지만, 기술 문서는 균일한 쪽이 맞습니다 (ko.react.dev 226개 문서: 합니다·습니다 9,435회, 해요 0회). 리듬을 위해 `~죠`, `~해요`를 섞지 않습니다 |
| 패턴 16 영어 관용구 직역 | **용어에는 적용하지 않습니다.** `state`를 "상태"로, `Hook`을 "훅"으로 바꾸려 하면 2단계 용어집이 우선입니다 |
| 「격식 유지」절의 어투 다양화 | 패턴 24와 같은 이유로 적용하지 않습니다 |

**결과 처리**

- humanizer가 내놓은 "자연스러운 버전"만 반영합니다. 분석 리포트를 사용자에게 그대로 옮기지 않습니다. 무엇을 고쳤는지 물으면 그때 간추려 답합니다.
- humanizer가 변경률 50%를 넘겨 중단하면, 문장 구조부터 다시 봅니다. 그 정도면 대개 3단계 번역투가 많이 남았다는 뜻입니다.
- humanizer가 용어나 코드 식별자를 건드렸으면 되돌립니다.

### 5. 점검합니다

- [ ] 문체가 한 가지로 통일됐는가 (UI 문구 인용만 예외)
- [ ] 같은 개념을 글 안에서 다른 말로 부르지 않는가
- [ ] 백틱이 코드 이름에만 붙었는가 (커밋 메시지에는 백틱이 없는가)
- [ ] 영어 표기 뒤 조사가 읽는 소리 기준으로 붙었는가
- [ ] 줄표(—)가 남아 있지 않은가
- [ ] 입력이나 코드로 확인되지 않은 사실(경로, 수치, 동작)을 쓰지 않았는가
- [ ] 요청에 없는 명령어, 예시, 링크, 섹션을 덧붙이지 않았는가 (필요해 보이면 본문 밖에서 제안)
- [ ] 4단계 대상 글이라면 humanizer를 **실제로 호출했는가** (없으면 직접 점검을 했고 그 사실을 알렸는가)
- [ ] humanizer를 거친 뒤에도 용어와 문체가 1~2단계에서 정한 대로인가
- [ ] 번역이면 [translating.md](references/translating.md) 5절 점검도 했는가

## 용어집을 키워 갑니다

용어집에 없는 단어를 판단했고 앞으로도 나올 것 같으면, 결과를 내놓을 때 정한 표기와 근거를 알리고 용어집에 추가할지 물어보세요. 그래야 다음 글에서도 같은 선택이 이어집니다. 절차는 [references/terms/adding.md](references/terms/adding.md)에 있습니다.
