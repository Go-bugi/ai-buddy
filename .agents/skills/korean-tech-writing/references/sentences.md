## 1. 문체

### 글 종류별 기본값

| 글 종류 | 문체 | 예 |
|---|---|---|
| README, 기술 문서, 번역 | 습니다체 | "캐시를 비운 뒤 다시 빌드합니다" |
| 여러 줄 코드 주석 | 습니다체 | "토큰이 만료되면 한 번만 재시도합니다" |
| 커밋 메시지, PR 제목, 이슈 제목 | 명사구 | "토큰 만료 시 재시도 로직 추가" |
| PR 본문, 이슈 본문 | 습니다체 | "만료된 토큰으로 요청하면 401이 반복되던 문제를 고쳤습니다" |
| UI 문구 | 해요체 | "저장됐어요", "다시 시도해 주세요" |
| 기술 블로그 | 습니다체 | |

우선순위는 이렇습니다.

1. 사용자가 문체를 직접 지정하면 그대로 따릅니다. 기술 블로그를 한다체로 써 달라는 요청 같은 경우입니다.
2. 저장소에 문체 규약 파일(`docs/korean-style.md`, `CONTRIBUTING.md`의 작성 규칙 등)이 있으면 그쪽을 따릅니다. 커밋 메시지는 `commitlint` 설정이나 기존 커밋 이력의 형식(Conventional Commits의 `feat:` 접두사 등)도 확인합니다.
3. 둘 다 없으면 위 표를 씁니다.

### 공통 규칙

- **한 글 안에서 문체를 섞지 않습니다.** 습니다체 문서에 `~해요`나 `~한다`가 끼어들면 바로 티가 납니다. 예외는 문서 안에서 UI 문구를 인용할 때뿐이고, 그 인용구만 해요체로 둡니다.
- **독자에게 시키는 문장은 `~하세요`** 입니다. "버튼을 클릭해 보세요". `~하십시오`는 쓰지 않습니다.
- **UI에서 요청할 때는 `~해 주세요`** 입니다. "입력해요"처럼 직역한 명령투는 쓰지 않습니다. 버튼처럼 짧은 라벨은 명사형("저장", "복사")으로 씁니다.
- **문서 헤딩은 명사형이나 `~하기`로 끝냅니다.** "state 변수 추가하기", "설치". 서술문 헤딩도 자연스러우면 괜찮습니다.
- **커밋과 제목은 명사구로 끝냅니다.** "레거시 필드 제거". `~를 제거한다`, `~를 제거했습니다` 같은 서술형은 쓰지 않습니다. 본문의 불릿 항목도 명사구로 끝맺습니다.
- **커밋 메시지에는 백틱을 쓰지 않습니다.** `git log`, GitHub 커밋 목록, 터미널은 마크다운을 렌더링하지 않아서 백틱이 문자 그대로 보입니다. "fix: useChatStore에서 리렌더링되지 않던 문제 수정"처럼 코드 이름을 그대로 씁니다. PR 제목과 본문, 이슈는 GitHub이 렌더링하므로 평소대로 백틱을 씁니다.

## 2. 문장 부호

### 줄표(—, –)를 쓰지 않습니다

산문, 주석, 커밋, PR, UI 문구 모두 마찬가지입니다. 문장 중간에 덧붙일 말이 있으면 쉼표나 콜론을 쓰거나, 문장을 나눕니다. 줄표는 영어 글의 습관이 그대로 옮겨 온 것이라 한국어 문장에서는 번역문처럼 보이고, 일부 에디터가 하이픈을 줄표로 자동 변환해서 diff가 지저분해지기도 합니다.

| ✗ | ✓ |
|---|---|
| 캐시를 비워야 합니다 — 그렇지 않으면 이전 빌드가 남습니다. | 캐시를 비워야 합니다. 그렇지 않으면 이전 빌드가 남습니다. |
| 세 가지 옵션 — A, B, C — 중 하나를 고르세요. | A, B, C 중 하나를 고르세요. |

범위는 `~`로 씁니다. "2~15초", "v18~v20".

### 가운뎃점(·)으로 기계적으로 묶지 않습니다

| ✗ | ✓ |
|---|---|
| 이름·이메일·전화번호를 입력하세요 | 이름, 이메일, 전화번호를 입력하세요 |
| 오류 확인·수정 작업 | 오류를 확인하고 고치는 작업 |

두 항목을 대등하게 묶을 때는 "및"이나 "와/과"를 씁니다. 표 안처럼 공간이 좁은 곳, 공식 명칭, 원문 인용은 예외입니다.

### 따옴표와 강조

- 화면에 보이는 문구, 메뉴 이름은 큰따옴표로 씁니다. "설정" 메뉴에서 "저장"을 누르세요.
- 굵게(`**`)는 한 문단에 한두 군데만 씁니다. 모든 문장에 굵게가 있으면 아무것도 강조되지 않습니다.

## 3. 번역투

번역투는 어휘 문제가 아니라 **문장 구조가 영어에 붙잡혀 있는 상태**입니다. 영어 원문을 번역할 때만 생기는 게 아닙니다. 영어 자료를 읽고 머릿속에서 옮겨 쓸 때도, LLM이 처음부터 한국어로 쓸 때도 똑같이 생깁니다. 그래서 이 절은 모든 글에 적용됩니다.

예시의 원문은 이 문서를 위해 만든 문장입니다.

### A. 인칭 대명사

영어는 주어를 반드시 채우지만 한국어는 문맥으로 압니다. `you`, `your`, `we`, `it`, `they`를 옮기면 문장이 바로 번역문처럼 읽힙니다. ko.react.dev도 "당신의"를 226개 문서에서 9회밖에 쓰지 않습니다.

| 원문 | ✗ | ✓ |
|---|---|---|
| You can pass props to your component. | 당신은 당신의 컴포넌트에 props를 전달할 수 있습니다. | 컴포넌트에 props를 전달할 수 있습니다. |
| We will look at this in the next section. | 우리는 이것을 다음 섹션에서 살펴볼 것입니다. | 다음 섹션에서 살펴봅니다. |
| It keeps its value between renders. | 그것은 렌더링 사이에 그것의 값을 유지합니다. | 리렌더링 사이에도 값이 유지됩니다. |

`you`가 독자에게 행동을 요구할 때는 대명사를 빼고 `~하세요`로 씁니다. "최상위에서 호출하세요".

### B. 피동과 행위자

행위자가 있으면 **능동으로 뒤집는 것**이 거의 항상 낫습니다.

| 원문 | ✗ | ✓ |
|---|---|---|
| This function is called by React. | 이 함수는 React에 의해 호출되어집니다. | React가 이 함수를 호출합니다. |
| The value is stored in a ref. | 값은 ref에 저장되어집니다. | 값을 ref에 저장합니다. |
| The component will be re-rendered. | 컴포넌트가 리렌더링되어질 것입니다. | 컴포넌트가 리렌더링됩니다. |

이중피동은 쓰지 않습니다. `되어집니다` → `됩니다`, `보여집니다` → `보입니다`, `불려집니다` → `불립니다`, `쓰여집니다` → `쓰입니다`, `잊혀집니다` → `잊힙니다`, `읽혀집니다` → `읽힙니다`.

행위자를 드러낼 필요가 없으면 생략합니다. "정의할 때 씁니다".

### C. 관사와 복수

| 원문 | ✗ | ✓ |
|---|---|---|
| Returns a function. | 하나의 함수를 반환합니다. | 함수를 반환합니다. |
| Components can have multiple states. | 컴포넌트들은 여러 개의 상태들을 가질 수 있습니다. | 컴포넌트는 여러 state를 가질 수 있습니다. |

"하나의"는 개수 1이 실제로 중요할 때만 씁니다. "정확히 하나의 값만 반환합니다". `~들`도 복수성이 문장의 요지일 때만 씁니다. "각 컴포넌트들은" → "각 컴포넌트는".

### D. 소유격 "의"

`of`와 `'s`를 전부 "의"로 옮기면 명사가 사슬처럼 이어집니다. 한국어는 명사를 그냥 붙여 복합어를 만듭니다.

| ✗ | ✓ |
|---|---|
| React의 컴포넌트의 state의 업데이트 | 컴포넌트 state 업데이트 |
| 함수의 매개변수의 기본값 | 함수 매개변수 기본값 |
| 이 화면의 옵션이 없습니다 | 이 화면에 옵션이 없습니다 |

**"의"가 한 문장에 두 번 이상 나오면** 하나로 줄일 수 있는지 봅니다. 위치를 말할 때는 "의"보다 "에"가 자연스럽습니다.

### E. 무거운 술어

| 영어 습관 | ✗ | ✓ |
|---|---|---|
| allows you to / lets you | ~하는 것을 허용합니다 | ~할 수 있습니다 |
| enables | ~을 가능하게 합니다 | ~할 수 있습니다 |
| provides | 기능을 제공합니다 | ~합니다 (동작을 직접 서술) |
| need to / have to | ~할 필요가 있습니다 | ~해야 합니다 |
| have / has | ~을 가지고 있습니다 | ~이 있습니다 |
| is located in | ~에 위치해 있습니다 | ~에 있습니다 |
| make sure to | ~하는 것을 확실히 하세요 | 반드시 ~하세요 |
| in order to | ~하기 위해서 | ~하려면 |
| It is important to note that | ~라는 점에 주목하는 것이 중요합니다 | (대개 통째로 삭제) |
| prevents A from B-ing | A가 B하는 일을 막아 줍니다 | (긍정으로 뒤집어) B하면 ~하기 때문입니다 |

`provides`는 그대로 옮기면 문장이 비어 보입니다. "이 Hook은 상태 관리 기능을 제공합니다"보다 "이 Hook은 state를 관리합니다"가 더 많은 정보를 담습니다.

**명사구를 앞세우는 틀**(`The key difference is that Y`)은 사실을 먼저 말하고 평가를 뒤에 붙이는 쪽이 자연스럽습니다.

✗ 쿠키를 다른 둘과 구별 짓는 성질은 HTTP 요청마다 서버로 실려 간다는 것입니다.
✓ 쿠키에는 나머지 둘에 없는 성질이 하나 있습니다. HTTP 요청마다 서버로 실려 간다는 것입니다.

지시 표현("이 표는", "아래 예시는")은 **한국어 글의 배치에서 무엇을 가리키게 되는지** 확인합니다. 영어 자료에서 맞던 지시가 옮겨 쓴 글의 배치에서는 틀릴 수 있습니다.

### F. 문장 길이와 관계절

영어 관계절은 뒤로 이어 붙지만 한국어 관형절은 앞으로만 붙습니다. 긴 관계절을 그대로 옮기면 수식어가 주어 앞에 쌓입니다.

✗ 두 개의 서로 다른 컴포넌트에서 사용되는, 동일한 이름을 가진 state 변수는 각각 독립적으로 관리되기 때문에 하나를 변경해도 다른 하나에는 영향을 주지 않습니다.

✓ 같은 이름의 state 변수를 서로 다른 두 컴포넌트에서 쓸 수 있습니다. 두 변수는 독립적이라, 하나를 바꿔도 나머지에는 영향이 없습니다.

**영어 한 문장이 한국어 두세 문장이 되는 것은 정상입니다.** 대응시킬 단위는 문장이 아니라 의미입니다. 쉼표, `which`, `and`, `but`, `so that` 자리가 대개 문장 경계 후보입니다.

### G. 접속과 전치사구

| 영어 습관 | ✗ | ✓ |
|---|---|---|
| If you want to..., then... | 만약 ~하기를 원한다면, 그러면 | ~하려면 |
| about | ~에 대해서 알아봅시다 | ~을 알아봅시다 |
| through / via | ~을 통해서 전달합니다 | ~으로 전달합니다 |
| in terms of | ~에 있어서 | (대개 생략) |
| as well as | ~뿐만 아니라 ~도 또한 | ~와 ~ |
| such as | ~와 같은 것들 | ~ 등 / 예를 들어 ~ |
| beyond X | X 너머 | 그 밖의 X |

"만약"은 `~면` 어미가 이미 조건을 표현하므로 대부분 불필요합니다. 접속사("그리고", "그래서")도 남발하지 않고 어미로 문장을 잇습니다.

## 4. AI 말투

LLM이 한국어를 쓸 때 남기는 흔적입니다. 영어 원문과 무관하게 생기므로 3절로는 걸러지지 않습니다. 다 쓴 뒤 `humanizer`로 한 번 더 검사하지만(SKILL.md 4단계), 처음부터 피하면 고칠 게 줄어듭니다.

- **과장과 거창한 해석**: "핵심적인 역할을 합니다", "획기적인", "강력한", "~의 증거입니다". 입력에 없는 평가를 덧붙이지 않습니다.
- **내용 없는 꼬리 문장**: 문단 끝에 앞 내용을 바꿔 말하는 요약, 요청하지 않은 전망이나 결론을 붙이지 않습니다. "이를 통해 더 나은 개발 경험을 제공할 수 있습니다" 같은 문장은 지웁니다.
- **기계적인 세 항목 나열**: 항목이 실제로 둘이면 둘만, 넷이면 넷을 씁니다. 리듬을 맞추려고 셋으로 맞추지 않습니다.
- **지어낸 사실**: PR 본문이나 문서에 파일 경로, 줄 수, 수치, 동작을 쓸 때는 실제 코드나 입력과 대조합니다. 확인하지 않은 내용은 쓰지 않습니다.
- **요청에 없는 덧붙임**: 사용자가 준 내용에 없는 설치 방법, 명령어, 예시, 링크, 주의 문구, "리뷰 포인트" 같은 섹션을 습관처럼 덧붙이지 않습니다. 그럴듯해 보여도 저장소의 실제 설정과 다를 수 있고(`corepack`으로 pnpm 설치, 훅 이름, 스크립트 이름 등), 사용자는 그걸 하나하나 확인해서 지워야 합니다. 꼭 필요해 보이면 본문에 넣지 말고, 결과를 내놓을 때 "이런 내용을 추가하면 좋겠다"고 따로 제안합니다. 입력에서 바로 따라 나오는 것(".env.example을 복사한다"를 `cp .env.example .env` 명령으로 보여주기)은 덧붙임이 아닙니다.
- **쉼표 과다**: 짧은 문장에 쉼표를 여러 개 넣지 않습니다. 쉼표가 둘 이상이면 문장을 나눌 수 있는지 봅니다.

## 5. 과잉 교정 주의

다듬는 것과 **내용을 바꾸는 것**은 다릅니다.

- **정보 삭제 금지**: 읽기 좋게 만든다고 조건, 예외, 경고를 빼지 않습니다. 문장을 나누되 내용은 다 담습니다.
- **없는 친근함 추가 금지**: "자, 그럼 한번 볼까요?" 같은 문장을 넣지 않습니다. 친절하되 담백하게 씁니다.
- **용어 과잉 한글화 금지**: "훅을 부르면 상태가 바뀝니다"가 아니라 "Hook을 호출하면 state가 바뀝니다". 용어는 [terms/common.md](terms/common.md)가 정합니다.
- **모든 피동 제거 금지**: 행위자가 없거나 중요하지 않으면 피동이 자연스럽습니다. "이 값은 캐시에 저장됩니다"는 문제없습니다. 문제는 이중피동과, 행위자가 뻔한데 굳이 피동을 쓰는 경우입니다.
- **문체 붕괴 주의**: 문장을 다듬다 보면 `~해요`나 `~한다`가 섞여 들어가기 쉽습니다.

## 6. 최종 점검
