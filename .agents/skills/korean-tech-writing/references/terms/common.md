# 용어 선택

어떤 단어를 영어 그대로 둘지, 음차할지, 한국어로 옮길지 정하는 기준입니다. 새로 쓰는 글과 번역 모두에 적용됩니다. 프레임워크 고유 개념어는 같은 폴더의 `<프레임워크>.md`에 있고, 두 곳이 어긋나면 **프레임워크 파일이 우선**합니다.

실측 수치는 `ko.react.dev` 원본 마크다운 226개 문서(`src/content`)에서 센 출현 횟수입니다. 아래 명령으로 재현됩니다.

```bash
scripts/measure-terms.sh https://github.com/reactjs/ko.react.dev.git src/content
```

## 1. 판단 순서

용어집(3~7절, 프레임워크 파일)에 있으면 그대로 따릅니다. 없으면 아래 순서로 판단합니다. 위에서 걸리면 거기서 멈춥니다.

1. **코드에 그대로 등장하는 이름, 제품명, 약어는 영어로 둡니다.** `useState`, `package.json`, React, TypeScript, API, CLI. 한글로 옮기면 산문과 코드의 연결이 끊기고, 독자가 검색할 수도 없습니다.
2. **공식 한국어 문서에 정착된 표기가 있으면 따릅니다.** 컴포넌트, 렌더링(음차), 반환, 호출(번역). 공식 문서는 많은 사람이 오래 다듬은 결과라 근거로 삼기 가장 좋습니다.
3. **공식 번역어가 현업에서 거의 안 쓰이면 현업 표기를 씁니다.** "경계 사례"보다 "엣지 케이스". 기준은 "한국 개발자가 PR이나 슬랙에서 이 번역어를 실제로 쓰는가"입니다. 공식 번역어가 현업에서도 충분히 쓰이면(반환, 의존성, 배포) 공식 쪽을 유지합니다. 6절에 확정된 예외 목록이 있습니다.
4. **정착된 표기가 없으면 한국어로 풀어 씁니다.** 억지 음차("배칭")나 억지 신조어를 새로 만들지 않습니다. "batching" → "일괄 처리", "여러 업데이트를 한 번에 처리".

판단 순서는 단어 하나를 정할 때 쓰는 도구입니다. 정한 뒤에는 **한 문서 안에서 같은 개념을 끝까지 같은 말로** 씁니다. 처음에 "의존성"이라고 썼으면 중간에 "디펜던시"로 바뀌면 안 됩니다. 일관성이 어느 표기를 골랐는지보다 중요합니다.

용어집에 없는 단어를 반복해서 판단하게 되면, 작업이 끝난 뒤 사용자에게 용어집에 추가할지 물어보세요. 추가 절차는 [adding.md](adding.md)에 있습니다.

## 2. 표기 규칙

### 백틱

**코드에 실제로 나오는 이름만** 백틱으로 감쌉니다.

| 백틱 O | 백틱 X |
|---|---|
| `useState`, `package.json`, `pnpm install`, `--force`, `NODE_ENV` | API, CLI, React, TypeScript, JSON, npm(도구 이름으로 말할 때) |

같은 단어라도 역할에 따라 갈립니다. "npm으로 설치합니다"의 npm은 도구 이름이라 백틱 없이, "`npm install`을 실행합니다"는 명령어라 백틱으로 씁니다.

예외로 **커밋 메시지에는 백틱을 쓰지 않습니다.** 커밋은 마크다운으로 렌더링되지 않아 백틱이 그대로 보이기 때문입니다. 자세한 내용은 [sentences.md](../sentences.md) 1절에 있습니다.

### 영어 병기

**번역어만 보고 원어를 떠올리기 어려울 때, 문서에서 처음 나올 때 한 번만** 병기합니다.

| 병기 O | 병기 X |
|---|---|
| 멱등성(idempotency), 재조정(reconciliation), 경쟁 상태(race condition) | 반환, 배열, 호출, 의존성 |

판단 기준은 "이 번역어로 검색했을 때 원하는 자료가 나오는가"입니다. 안 나올 것 같으면 병기합니다. 매번 병기하면 글이 괄호투성이가 되니 첫 등장 한 번이면 충분합니다.

### 조사

영어 표기 뒤 조사는 **철자가 아니라 한국어로 읽었을 때의 받침**으로 정합니다. 받침이 있으면 `을/은/이`, 없으면 `를/는/가`입니다.

| 표기 | 읽는 소리 | 받침 | 을/를 | 은/는 | 이/가 |
|---|---|---|---|---|---|
| component | 컴포넌트 | 없음 | 를 | 는 | 가 |
| DOM | 돔 | ㅁ | 을 | 은 | 이 |
| API | 에이피아이 | 없음 | 를 | 는 | 가 |
| HTML | 에이치티엠엘 | ㄹ | 을 | 은 | 이 |
| CSS | 씨에스에스 | 없음 | 를 | 는 | 가 |
| URL | 유알엘 | ㄹ | 을 | 은 | 이 |
| JSON | 제이슨 | ㄴ | 을 | 은 | 이 |
| npm | 엔피엠 | ㅁ | 을 | 은 | 이 |
| Git | 깃 | ㅅ | 을 | 은 | 이 |
| Docker | 도커 | 없음 | 를 | 는 | 가 |
| Redis | 레디스 | 없음 | 를 | 는 | 가 |
| PR | 피알 | 없음 | 를 | 는 | 가 |

백틱 뒤에도 같습니다. `` `useState` ``(유즈스테이트) → `` `useState`를 ``, `` `ref` ``(레프) → `` `ref`를 ``.

## 6. 공식 번역어보다 현업 표기를 택하는 경우

판단 순서 3단계에 해당하는 확정 목록입니다. 공식 번역어가 있지만 현업에서 거의 쓰지 않는 것들이라 음차나 원문을 씁니다.

| 영어 | 쓰는 표기 | 쓰지 않는 표기 |
|---|---|---|
| edge case | 엣지 케이스 | 경계 사례 |
| fallback | 폴백 | 대체, 대비책 |
| side effect | 사이드 이펙트 | 부수 효과. React 문맥에서는 `Effect`와 이어지는 점도 있습니다 |
| trade-off | 트레이드오프 | 상충 관계 |
| refactoring | 리팩터링 | 재구조화 |
| debugging | 디버깅 | 오류 수정 |
| rollback | 롤백 | 되돌리기(일반적 의미일 때는 "되돌리기"도 자연스럽습니다) |
| hotfix | 핫픽스 | 긴급 수정 |
| boilerplate | 보일러플레이트 | 상용구 |
| race condition | 경쟁 상태(race condition) | 공식 번역어가 현업에서도 쓰여서 유지하되, 첫 등장에 병기합니다 |

이 목록에 항목을 추가할 때는 "공식 번역어가 있다"와 "현업에서 거의 안 쓴다"를 둘 다 만족하는지 확인합니다. 하나만 만족하면 1절 판단 순서대로 처리합니다.

## 7. 문맥에 따라 갈리는 용어

| 영어 | 후보 | 선택 기준 |
|---|---|---|
| list | 목록 224 / 리스트 82 | 일반적 의미면 "목록", UI 요소 이름이면 "리스트" |
| attribute | 어트리뷰트 58 / 속성 143 | HTML·JSX·템플릿 어트리뷰트를 가리키면 "어트리뷰트" |
| state | 원문 유지 / 상태 410 | 프레임워크의 state API를 가리키면 원문 유지, 일반적인 "상태"면 번역 |
| argument | 인수 116 / 인자 60 | "인수" |
| batching | 일괄 처리 | 정착된 음차가 없습니다 |
| user | 사용자 / 유저 | 문서에서는 "사용자". "유저"는 쓰지 않습니다 |
| issue | 이슈 / 문제 | GitHub 이슈처럼 트래커 항목이면 "이슈", 일반적인 문제면 "문제" |

`attribute`는 빈도만 보면 "속성"이 두 배 넘게 많지만, 그 숫자에는 일반적 의미의 "속성"(객체의 속성, 어떤 것의 성질)이 섞여 있습니다. 빈도표를 볼 때는 이런 동음이의 오염을 항상 의심하세요. 숫자만 보고 정하면 틀립니다.

다만 쿠키의 `Expires`·`Max-Age`·`Domain`·`Path`·`Secure`는 "속성"입니다. 영어로는 똑같이 attribute지만 HTML 어트리뷰트가 아니라 RFC 6265가 정의한 별개 개념이고, 한국어 웹 문서도 "쿠키 속성"으로 굳어져 있습니다. `attribute`를 보면 무조건 "어트리뷰트"로 옮기지 말고 어느 명세의 attribute인지 먼저 확인하세요.
